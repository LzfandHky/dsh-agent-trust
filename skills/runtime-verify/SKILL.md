# 运行时验证

一句话：**能自己运行并观察真实产物的 agent，才开始值得信任。**
单元测试绿只证明"函数对"，运行验证才证明"功能对"。

## 铁律

1. **先复现，再修。** 修改前必须让缺陷稳定重现一次，并记录条件下手。
2. **验证范围必须覆盖缺陷范围。** 用户点了按钮，就要真的点那个按钮，不能只跑单测。
3. **断言可观测终态，不 sleep。** 轮询"完成状态"（元素出现、文字变化、接口返回、进程退出）。
4. **全程收集控制台/日志。** 交付时报告错误数为 0 或有几条例外。
5. **无法验证必须明说。** "环境缺依赖，无法验证" 永远好过"应该可以"。
6. **禁止改测试期望值来通过。** 那是把验证废掉。

## 闭环六步

| 步 | 动作 | 输出 |
|---|---|---|
| 1 | 启动真实构建（开发服务器/打包产物/模拟器/CLI） | 进程与访问地址 |
| 2 | 载入预置登录态与测试数据 | 已登录会话，无残留弹窗 |
| 3 | 按功能地图导航到目标界面 | 到达目标状态的证据 |
| 4 | 执行用户动作（优先语义选择器、快捷键） | 动作已生效 |
| 5 | 轮询终态 + 收集控制台 | 状态断言通过、错误列表 |
| 6 | 报告命令、期望 vs 实际、未验证项 | 证据包 |

## 选择器纪律

按优先级选：`role/aria-label` → `data-*` 测试属性 → 语义文本 → CSS 类（最后手段）。
坐标点击是最后的选择：它绕过快捷键代码路径，也不反映真实可访问性。
用快捷键时要确认它确实被注册了，而不是碰巧落到了别处。

## 缺陷修复的验证模板

```
1. 准备测试数据与账号
2. 修复前：在目标界面复现问题，记录触发条件与截图/日志
3. 修改代码
4. 相同条件下重试，确认现象消失
5. 刷新/重进页面，确认状态被持久化（读接口也返回新值）
6. 跑一条能复现该缺陷的回归测试 + 相关既有测试
7. 报告：执行了什么命令、期望与实际、哪一项没验证及原因
```

## 各平台的"跑起来"入口

| 平台 | 典型手段 | 能观察到什么 |
|---|---|---|
| Web / Electron | 浏览器调试协议（CDP）、Playwright、内置调试端口 | DOM、控制台、网络、性能轨迹、内存快照 |
| iOS | 模拟器命令行工具、无障碍树 | 界面状态、崩溃日志、性能 |
| CLI / 后端 | 真实命令 + 真实依赖、请求日志 | 退出码、stdout/stderr、接口响应 |
| 桌面应用 | 系统级自动化 API（Windows UIA / macOS AX） | 控件树、窗口状态、截图 |

不要用 mock 替代"能不能真的跑"。mock 适合隔离，不适合当结论。

## 交付格式

```
验证方式：<命令/脚本>
进入路径：<如何到达该界面>
复现（修改前）：<现象 + 证据>
验证（修改后）：<现象 + 证据>
控制台错误：0（或列出）
未验证项：<明确列出，含原因>
```

## 与其它技能的衔接

- 不知道"怎么走到那个界面" → `feature-map`
- 不知道"为什么坏" → `evidence-first-debug`
- 想知道"这套验证本身可靠吗" → `skill-eval`
