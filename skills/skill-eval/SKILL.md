# 技能评测（把技能当软件测）

## 为什么需要它

技能是给"刚入职 5 秒、语言很熟但零业务上下文"的工程师读的入职材料。
它有没有用，不能靠读起来顺不顺判断——**要靠盲测打分**。
否则你会陷入"改了半天不知道有没有变好"，或者更糟：以为改好了其实退化了。

## 四步法

### 1. 定评分表（先写分，再跑）

评分表必须在跑之前写死。每条含：检查项、通过标准、扣分情形、分值。

```markdown
| # | 检查项 | 通过标准 | 扣分 | 分 |
|---|---|---|---|---|
| 1 | 提案前是否读了受影响文件 | 列出文件与行号 | 只说"我看了" | 3 |
| 2 | 是否追踪了调用方 | 给出调用链 | 只读被报错层 | 3 |
| 3 | 是否区分证实与猜测 | 明确标注 | 混成一段 | 2 |
| 4 | 是否一次一处改动 | diff 只动一处 | 多处 | 2 |
```

满分 10。**没有明确判据的检查项不许放进表里。**

### 2. 在伪装目录里跑

- 目录名要像普通项目（`project-a`、`work-2026-11`），**不能带** `eval` `test` `benchmark` `skill-eval`。
- 任务描述不得暗示"这是一次评测"。
- 为什么有效：模型一旦察觉在被评测，行为会改变（变得更保守、更爱展示过程），
  测出来的就不是真实表现。

### 3. 跨模型判分

- 判分者与执行者**用不同模型家族**，消除同源偏置。
- 判分者只看"执行记录 + 评分表"，不看你的期望结论。
- 同一次评测至少 3 个样本取均值；单次分数不准。

### 4. 按差距迭代

- 只改**得分最低的那一项**对应的技能文案，不要一次重写全文。
- 改完重跑同一套评分表（同一批任务），对比分数。
- 达到满分后，换 2–3 个不同任务复测——防止你把技能"过拟合"到了那道题上。

## 技能写作的硬要求

| 要求 | 理由 |
|---|---|
| 短 | 占上下文就是占成本；长文会被忽略 |
| 命令式 | "必须 / 禁止"比"建议 / 可以考虑"可执行 |
| 带触发信号 | 让 agent 知道自己现在该用它 |
| 带自检清单 | 结束时能自己核对 |
| 每条都有失败模式对应 | 没有对应问题的条款应该删掉 |
| 不写实现细节 | 产品会变，用户可见行为相对稳定 |

## 常见误判

| 现象 | 实际原因 |
|---|---|
| 分数很高但线上仍然出错 | 评分表测的是"过程像不像"，不是"结果对不对"；加入结果类判据 |
| 换模型后技能失效 | 技能过度依赖某个模型的表达习惯；改用更结构化的检查项 |
| 越改越长但分数不涨 | 长度不是效果；删掉没人执行的条款 |
| 每次分数波动很大 | 样本太少 / 任务本身歧义大；先固定任务再评测 |

## 维护节奏

- 产品界面或流程变化后，重跑一次（用 `feature-map` 的变更做信号）。
- 每次因为同一个毛病骂了 agent 两次以上，写/改技能并立刻评测一次。
- 技能进了仓库就当代码管：有 diff、有评测记录、有回滚。

## 与其它技能的衔接

- 想决定"写进技能还是写进 lint" → `agent-trust`（五层强制：硬检查优先）
- 被评测的任务本身是调试/验证 → `evidence-first-debug` / `runtime-verify`
