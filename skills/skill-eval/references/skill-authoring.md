# 技能文件规范

## 结构

```
skills/<kebab-name>/
  SKILL.md              # 必需：frontmatter + 正文
  references/<name>.md  # 可选：按需读取的细节
  scripts/              # 可选：可执行辅助
```

## frontmatter

```yaml
---
name: kebab-case-name
description: >
  一两句说明它做什么；然后列触发场景（用户会怎么说、什么任务像它）；
  最后写 Do NOT trigger for: 指向该用的其它技能。
metadata:
  origin: 来源或版本备注
---
```

要点：

- `description` 同时是**目录摘要**，也是模型判断"要不要用它"的唯一依据。
  因此触发词要写"用户的原话"，不要只写抽象概念。
- 排他说明很重要：没有 `Do NOT trigger` 的技能会到处抢活。
- `name` 用 kebab-case，与目录名一致。

## 正文骨架

```markdown
# 标题

一句话说明本质（不要复述 frontmatter）

## 铁律 / 原则        # 3–6 条，命令式
## 流程              # 表格或编号，每步有产出
## 模板 / 示例        # 可直接套用
## 常见坑            # 症状 → 原因 → 处理
## 与其它技能的衔接   # 避免重复造轮子
## 参考              # 指向 references/
```

## 长度

- 主文件 ≤ 150 行。超了就把细节切到 `references/`。
- 一条规则一行为单位；段落超过 4 行就该改成列表。
- 删掉"大家都知道的道理"（如"要仔细"、"注意质量"）——它们不改变行为。

## 好条款 vs 坏条款

| 坏 | 好 |
|---|---|
| 仔细阅读相关代码 | 提案前列出你读过的文件与行号 |
| 注意性能 | 断言长任务不超过每帧 16ms，超了即失败 |
| 保持代码整洁 | 禁止新增代码注释；不变量写进架构文档 |
| 尽量验证 | 无法验证时必须写明"未能验证"及原因 |
| 多使用子智能体 | 根因结论前，至少派 1 个子智能体追踪调用方 |

判据：**读者能否仅凭这句话判断"我做到了没有"？** 不能，就重写。

## 反模式

1. **百科式**：把领域知识全倒进去，执行者读不完。→ 只留改变行为的条款。
2. **抒情式**："作为一个优秀的工程师……" 无判据。
3. **不可测式**：写"要稳健"，但不说什么算稳。
4. **重复式**：同一条在三个技能里各写一遍，改一处漏两处。→ 用衔接段指向主技能。
5. **过拟合式**：为了过某道评测题写的特殊条款。→ 换任务复测会暴露。
6. **代码细节式**：写死内部函数名和路径。→ 产品一改就废，写用户可见行为。

## 提交前自检

- [ ] frontmatter 有 name 与 description，且含排他说明
- [ ] 每条规则都能判定"做到没有"
- [ ] 主文件 ≤ 150 行，细节在 references/
- [ ] 没有和其它技能重复定义同一规则
- [ ] 至少有一条"常见坑"，来自真实失败
- [ ] 跑过一次盲测（见 `rubric-template.md`）
