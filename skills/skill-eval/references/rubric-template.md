# 评分表模板与判分流程

## 模板

```markdown
# 评分表 — <技能名> v<N>

评测目标：验证该技能是否让 agent 稳定做到 <行为>
任务集：T1 <描述> / T2 <描述> / T3 <描述>
满分：10（每项分值为整数，合计 10）

| # | 检查项 | 通过标准（可观察） | 扣分情形 | 分 |
|---|---|---|---|---|
| 1 | | | | |
| ... | | | | |

总分换算：
- 9–10 可用；6–8 需改；≤5 重写
- 任一项得 0 分（完全没做）时，即使总分达标也判不合格

## 样本与判分
- 每个任务跑 3 次，取均值
- 判分者：<与执行者不同模型家族>
- 判分输入：仅执行记录（工具调用 + 输出），不含我的结论
- 记录：附每项的判分理由一句话
```

## 判分流程

1. 协调者先写评分表（**在跑之前**），并发给判分者。
2. 执行者：在伪装目录中收到普通任务描述，不知道有评分表。
3. 收集执行记录：工具调用序列、每步输出、最终答复。
4. 判分者逐项打分，给出理由；不参与修改技能。
5. 协调者汇总：找最低项 → 只改那一项相关文案 → 重跑。

## 判分者提示词骨架

```
你会拿到一份评分表与一段执行记录。
逐项判断执行记录是否满足"通过标准"，输出：
- 该项得分（0 / 部分 / 满分）
- 一句话依据（引用执行记录中的具体证据）
不得根据自己的偏好加减分；标准未覆盖的情形记 0 并说明。
```

## 防止评测被"游戏化"

- 目录名、任务名、文件路径都不出现评测字样。
- 不要把评分表放进被执行者能读到的目录。
- 如果某个技能被频繁评测，轮换任务描述，避免执行者记住措辞。
- 观察执行记录是否出现"为了看起来合规而增加多余步骤"——这也是被察觉的信号。

## 一份能用的最小检查项集合（调试类技能）

| 检查项 | 判据 |
|---|---|
| 读到受影响文件 | 记录中有对具体文件与行的读取 |
| 追踪调用方 | 提及调用位置或以调用链解释 |
| 假设具体 | 假设含位置 + 机制 |
| 一次一处改动 | diff 只涉及一处逻辑变更 |
| 区分证实与猜测 | 明确标注未证实项 |
