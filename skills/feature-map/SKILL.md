# 功能地图（Feature Map）

## 它解决什么问题

agent 会启动应用、会截图，仍然会失败——因为**它不知道你的产品长什么样**。
一份"用户视角"的地图把"侧边栏"这种含糊词变成一个可执行的到达路径。

关键取舍：**写用户看到的东西，不写内部实现细节。** 内部代码每天都在变，
"用户怎么到达这个界面、成功后看到什么"相对稳定。

## 目录结构

```
feature-map/
  _index.md              # 界面清单 + 一句话职责 + 到达方式索引
  <surface>.md           # 一个用户可见界面一份，如 sidebar.md
  cross-cutting-flows.md # 跨界面的动作流，如"新建任务→后台队列→通知"
```

一个文件一个界面。**不要写成一个巨型 README**——按需读单文件才是它省 context 的原因。

## 单份文件模板

```markdown
# <界面名>

## 这是什么
（一句话：用户在这里完成什么）

## 如何到达
1. 从 <起点> 点击 <可识别元素>
2. 或使用快捷键 <组合键>
3. 前置状态：<需登录 / 需先创建 X / 需选择某项目>

## 主要动作
| 动作 | 触发方式 | 期望结果 |
|---|---|---|
| <做某事> | 点击 <元素> / 快捷键 | <界面上出现的可观测变化> |

## 成功后的可观测状态
- <元素出现 / 文本变为 / 请求返回 / 列表新增一条>
- 判据要具体到"能断言"，不要写"看起来正常"

## 稳定选择器
| 元素 | 标识 | 类型 |
|---|---|---|
| <元素> | `[data-action-id="..."]` | data 属性 |
| <按钮> | `role=button[name="..."]` | 语义 |

## 常见异常
- <现象> → 先检查 <原因> → 处理 <方法>
```

## 四条硬规范

1. **用户视角单文件**：一个界面一份，按需读取；不要串成一篇长文。
2. **基线前置**：写清"进入前必须已具备什么"（登录态、初始数据、默认分组）。
   否则每次验证都从脏状态开始。
3. **语义选择器**：优先 aria 标签与 `data-*` 属性；避免 CSS 类名和坐标点击。
   顺带记录快捷键——它往往是被测代码里最容易被忽略、也最容易坏的路径。
4. **可观测终态**：写"什么时候算完成"，供轮询使用；异步/流式界面尤其重要。

## 怎么生成

1. 从入口开始，逐个界面走一遍（或用代码搜索找到路由/视图注册点）。
2. 每到一个界面，记录：职责、到达路径、主要动作、成功后标志、可用的稳定标识。
3. 记录跨界面的流程（提交后去了哪、异步结果怎么回来）。
4. 对每个"成功标志"自问：**这条能不能被程序断言？** 不能就改写。

## 怎么维护

- 改动触及某界面时，同步更新那一份文件；只改一个文件，成本极低。
- 验证失败但"地图上写着能到达"→ 说明地图已过期，改地图而不是改结论。
- 每次新增界面，先加地图再写代码（顺序反了就会漏）。

## 处理低质量反馈

用户给的信息通常是："侧边栏卡"、"打不开"、一张截图、或三个问号。
处理流程：

1. 用关键词匹配到界面文件（`_index.md` 的职责列）。
2. 用"如何到达"复现出同一界面。
3. 用"成功后的可观测状态"对比现状，得到具体差异。
4. 差异才是需求，原始反馈不是。

这一步做完，你才真正"读懂"了那条模糊反馈——这也是地图最大的价值。
