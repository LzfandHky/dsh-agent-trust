# 强制手段落地检查单

按顺序做，每条独立提交、独立回滚。**先做能机械失败的，再做需要人记的。**

## 第一层：结构拓扑

- [ ] 选定一个最常被改的功能，把它散落各处的代码收敛进一个目录
- [ ] 在该目录内建立约定：入口、状态、视图、测试都在目录内
- [ ] 新功能创建流程只需"建目录 + 填保留文件名"，无需改中央注册表
- [ ] 检查是否仍存在"新建任何东西都要改的那个文件"——有就拆掉
- [ ] 层间依赖改为单向（框架层不 import 产品层）

验收：**新同事或 agent 拿到一条需求，不需要全局搜索就知道代码该放哪。**

## 第二层：静态分析（让 CI 变红）

从"最近三次人工评审意见"里挑，不要凭空设计规则。

- [ ] 列出现有 lint 配置，确认 agent 能看到并执行（不是只配了没跑）
- [ ] 加第一条禁用规则：最高频的危险写法
- [ ] 加依赖图检查：禁止跨层引用（尤其主进程/渲染进程、框架/产品）
- [ ] 加"新增代码注释"检查（只查 diff 新增行，历史存量豁免）
- [ ] 每条规则配一条"违规示例"文档，说明为什么会红

验收：**故意写一次错误写法，CI 必须变红，且报错信息能指导修复。**

规则写法要点：

| 要点 | 说明 |
|---|---|
| 只查 diff 新增 | 存量不动，避免一次性几千条报错 |
| 报错给修复建议 | 只说"不允许"会让 agent 反复试 |
| 豁免要显式 | 白名单文件 + 理由 + 评审；不要静默跳过 |
| 一条规则一件事 | 复合规则难排查 |

## 第三层与第四层：规则文件与技能

- [ ] AGENTS.md 里只写"本项目特有的、别处查不到的"约定，重复通用知识会稀释注意力
- [ ] 每条约定指向对应的硬检查（"见 CI 规则 X"），让软规则成为硬规则的向导
- [ ] 技能里写的必须是**可判定**的检查项，而非愿望

## 第五层：风格指南与评审

- [ ] 每次写评审意见时，同步判断：这条能不能变成第 1–2 层？
- [ ] 建立"评审意见 → 规则"的台账，每周看一次未转化的积压
- [ ] 反复出现的意见超过 2 次，升级为强制项

## 反模式（做了会白做）

- 只加规则不收结构：agent 仍会在错的目录里写对的代码。
- 规则一次上 20 条：没人能定位是哪条挡住，最后全员豁免。
- 豁免静默生效：等于规则不存在，还给人虚假安全感。
- 把不变量写进代码注释：注释在 diff 里没有约束力，且污染上下文。
- 只靠 AGENTS.md 和评审：人类注意力耗尽那天，仓库开始腐化。

## 一个最小可行起点

如果你只能改一件事：**挑一个功能收敛成单目录，并加一条依赖图 CI。**
这两件事加起来的收益，大于写一整本规范文档。
