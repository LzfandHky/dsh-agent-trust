# 证据优先的调试

## 核心失败模式

agent 看到报错 → 在脑子里匹配一个常见原因 → 自信宣布"找到了" → 改一处 → 没好 → 换一处。
整条链上**一次都没打开过真正相关的文件**。这比慢更糟：它消耗你对它的信任。

## 铁律

1. **没读文件，不许给根因。** 提案前必须列出你读过的文件与关键行。
2. **追踪调用方。** 只看被报错的那一层是不够的，要看谁调它、传了什么、在什么条件下。
3. **区分三种陈述**：已观察（有输出）、已推断（有依据但未验证）、已猜测（无依据）。
   交付时必须分开写，不许混成一段自信的话。
4. **一次一个假设。** 同时改三处，等于放弃了定位能力。
5. **解释"为什么现在才坏"。** 如果说不清触发条件，你大概率改的不是根因。

## 流程

| 步 | 动作 | 产出 |
|---|---|---|
| 1 | 复现：记录触发条件与稳定复现步骤 | 可重复的现象 |
| 2 | 定位范围：报错栈 → 入口 → 相关模块 | 候选文件清单 |
| 3 | **读代码**：逐个打开候选文件，读实现与调用方 | 关键行引用 |
| 4 | 形成假设：一句话说明"因为 X，所以 Y" | 可被推翻的假设 |
| 5 | 设计判别实验：能区分假设真假的观察/命令 | 实验与预期 |
| 6 | 执行实验 → 得到证据 → 接受或推翻 | 证据 |
| 7 | 只改一处 → 重复实验 | 变化对比 |
| 8 | 报告：证据 / 结论 / 未证实部分 | 交付 |

第 3 步是最常被跳过的一步，也是最该被强制的一步。

## 假设的写法

坏假设："可能是状态更新有问题。"
好假设："因为 `useEffect` 依赖数组漏了 `sessionId`，切换会话时不会重新拉取数据，
所以界面停留在上一个会话的内容。"

好假设有三个特征：指向具体位置、说明机制、能设计出判别实验。

## 判别实验的优先级

1. 能直接打印/观察中间值的（日志、断点、探针）——最快。
2. 能二分定位的（注释掉一半、回退到上一个提交）——适合回归。
3. 对比实验（改前 vs 改后跑同一路径）——适合验证修复。
4. 加监控长期观察——最后手段。

## 回归专用：二分

```
git log --oneline <已知好提交>..<已知坏提交>   # 列出可疑区间
# 对区间中点构建并验证；好则往后半段找，坏则往前半段找
```
不要在没读过 diff 的情况下"感觉是那个改动"。二分给出的是事实，不是直觉。

## 交付模板

```markdown
## 根因分析

### 现象
（可复现步骤 + 观察到的错误）

### 已读证据
- `path/to/file.ts:42-58` — <这里发生了什么>
- `path/to/caller.ts:12` — <以什么参数调用它>

### 根因（已证实 / 待证实）
<一句话机制说明>

### 判别实验
- 实验：<命令或观察>
- 预期：<若假设成立会看到什么>
- 实际：<看到了什么>

### 改动
- 只改了：<文件:行>
- 为什么这样改能解决：<对应根因>

### 未能证实
- <项> — 原因
```

## 何时停止挖

根因挖到"改了它现象消失，且能解释为什么"就可以停。
不要为了完美理解去重构整条链——那会把修复变成项目。
但如果**现象消失而你说不出为什么**，那不算修好，只是把问题挪了个位置。

## 与其它技能的衔接

- 需要跑起来才能取证 → `runtime-verify`
- 这条教训要不要写成规则 → `agent-trust`（五层强制）
- 反复在同一个地方出错 → `skill-eval` 或 `agent-ready-architecture`
