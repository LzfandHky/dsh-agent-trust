# 五阶段落地手册

每个阶段给出：做什么、产出物、验收门、常见卡点。**不要跳过验收门。**

## 阶段 1：本地运行时验证 + 功能地图

- 做什么：让 agent 能启动真实程序、驱动界面、读控制台、截取性能/内存信息；
  为每个核心界面写一份"用户视角"的功能地图（见 `feature-map`）。
- 产出物：一个可执行的验证脚本或命令 + `feature-map/` 目录。
- 验收门：**在预置好的登录态下，agent 独立走完一条核心路径，控制台 0 报错，且能贴出它看到的状态。**
- 卡点：登录态难准备（用现成的用户数据目录克隆，别每次走 OAuth）；
  弹窗/toast 残留干扰（启动时清理）；固定 sleep 代替状态轮询（改成轮询可观测状态）。

## 阶段 2：失败模式技能化

- 做什么：跑 1–2 个 agent，**打开它的工具调用和思考过程**看它在哪里走偏；
  每次只把一个复发毛病写成一个技能条目（不是写一本规范书）。
- 产出物：3–5 个针对性技能，每个含"触发信号 → 必须做 → 禁止做 → 自检"。
- 验收门：**同类任务再跑一次，agent 在提案前贴出了文件读取证据/调用链。**
- 卡点：写得太大太全（技能要短、要可执行）；写成了"愿望"而不是"检查项"。

## 阶段 3：盲测与爬坡

- 做什么：给核心技能写评分表；在**伪装过的目录名**里并行跑子任务；
  用**不同模型家族**的判分者打分；按分差改技能文案，循环到满分。
- 产出物：评分表 + 一轮对照记录（改前/改后分数）。
- 验收门：**核心技能在目标模型矩阵上稳定拿满分，且被评测者没有察觉自己在被评测。**
- 卡点：同模型自评（要跨模型判分）；目录名带 "eval/test/benchmark"（模型会改行为）；
  只测一次（噪声大，至少 3 次取样）。

## 阶段 4：人工评论转硬检查

- 做什么：把反复出现的评审意见逐条转成 lint / AST 规则 / 依赖图检查；
  同时把"一个大功能散落在多处"的结构收敛成单目录。
- 产出物：新增的 CI 规则 + 结构收敛的 PR。
- 验收门：**曾经需要人来说的那三类问题，现在直接 CI 变红。**
- 卡点：规则写得太宽导致大量豁免（豁免要显式、要评审，别默默跳过）；
  只加规则不收结构（结构是最硬的那层）。

## 阶段 5：云端队列与角色分工

- 做什么：先只部署一个"复现专员"（拿到问题→在隔离环境复现→对比当前主干）；
  跑稳后再加协调者与并行执行者，并写清交接契约。
- 产出物：复现专员的自动回复 + 角色交接契约 + 原子 PR 规范。
- 验收门：**云端能自动区分"这是旧版本的问题（主干已修）"与"主干仍有问题"。**
- 卡点：本地还没稳就上云（烧钱且噪音大）；一个 PR 塞进几千行（无法回滚）。

## 交接契约模板（阶段 5 用）

```
角色：隔离的功能执行者
工作区：独立分支/工作树；只改分配到的功能目录，除非明确要求架构变更
动工前：
1. 读遍相关文件并追踪调用方，没有文件证据不得提出根因
2. 用验证技能启动真实构建，载入预置登录态，按功能地图导航（语义选择器 + 快捷键）
3. 复现基线行为或缺陷，保存运行时日志/轨迹
实现要求：
- 遵守硬约束（禁用 API、禁闲聊式注释、跨进程依赖隔离）
- 保持改动原子，可在主干上独立回滚
- 验证时轮询可观测终态，断言 0 控制台错误
返回：改动文件清单、复现对比（旧提交 vs HEAD）、验证输出、回滚命令
```

## 授权前的最低门槛（三选三）

1. 一个 agent 在预置环境下独立复现过 1 个真实缺陷，0 报错。
2. 至少 1 个核心技能通过了伪装目录下的跨模型盲测。
3. 已有 3 条人类评审意见被转成了会让 CI 变红的检查。

三条不全，不要给云工人分支写权限。
