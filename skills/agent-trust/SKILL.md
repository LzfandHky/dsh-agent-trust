# 智能体信任工程（总入口）

核心命题：**产出速度不是瓶颈，可托付程度才是。** 一个 agent 写得多快不重要，重要的是
"没有我在场时，它能自己推进多远"。信任不是态度问题，是可建造的机制问题。

本技能是套件的路由与总纲。按任务选分技能：

| 你面对的情况 | 用哪个技能 |
|---|---|
| 要让 agent 真的把程序跑起来、自己看结果 | `runtime-verify` |
| 用户只丢来一句"侧边栏卡"或一张截图 | `feature-map` |
| agent 第 100 次宣布"找到根因了"但其实没读代码 | `evidence-first-debug` |
| 想确认某个技能/SOP 真的有效、改完没退化 | `skill-eval` |
| 想从结构上让 agent 默认写出好代码 | `agent-ready-architecture` |
| 不知道现在该投哪一步、顺序怎么排 | 本文件 §2 与 §4 |

## 1. 信任曲线：四个档位

把"我在环里的程度"当成变量，而不是把"agent 行不行"当成结论。

| 档位 | 你的行为 | 上限 | 升级的硬条件 |
|---|---|---|---|
| L0 人肉传声筒 | 跑起来→截图/报错复制给 agent→等它改 | 1 个并发 | 装好运行时验证闭环 |
| L1 有验证的本地观察 | agent 自己跑起来、自己看、自己改 | 2–5 个并发 | 复发失败模式已写成技能 |
| L2 局部放手 | 只审"证据包"，不逐行读码 | 5–15 个 | 硬约束（lint/CI/结构）就位 |
| L3 无人值守 | 过夜合并，次日看结果 | 10+ / 云队列 | 原子回滚 + 事后巡检 |

规则：

- **跳档必失败。** 从 L0 直接铺 100 个 agent，只是更快地生产垃圾，而且更贵。
- 每次感到"还是我自己看一下放心"，都把它当成一条需求：**缺的是哪一层机制？**
- 上升靠机制，不靠勇气；下降不丢人，回 L1 补机制再上。

## 2. 五层强制：把纠错放在最硬的那层

同一件事（例如"别在渲染线程里做重活"）可以写在五个地方，强度差很多。
**永远优先往上打，而不是反复在下面嚷嚷。**

| 层 | 手段 | 硬度 | 失效方式 |
|---|---|---|---|
| 1 结构拓扑 | 一个功能一个目录、单向依赖、保留文件名自动发现 | 最硬 | 需要前期重构 |
| 2 静态分析 | lint / 编译器 / CI 依赖图 / 禁用 API | 硬（CI 变红） | 需要写规则 |
| 3 规则文件 | AGENTS.md、仓库约定 | 软 | 模型会漏读 |
| 4 技能 playbook | 本套件这类 Markdown 技能 | 软 | 需要维护与盲测 |
| 5 风格指南/人工评审 | 散文规范、PR 评论 | 最软 | 人类注意力耗尽 |

判断法则：

- **每写一条 PR 评论，问一次**："这条能不能变成 lint 规则 / CI 检查 / 结构上的不可能？"
- 只有第 3–5 层在防线的仓库，长期必然退化。这不是模型问题，是物理。
- 第 5 层不是零价值：它是**新规则的采样器**。它的产出物应该是第 1–2 层的规则，而不是更多评论。

## 3. 验证优先于生成

- "它说它改了" ≠ "它验证了"；"单元测试绿了" ≠ "用户路径通了"。
- 一个 agent 能自己**运行并观察**真实产物，比它多聪明都重要：
  这决定了它能否自行闭环，而不是每次回来问你。
- 正确性与质量是两件事：验证保证"功能是对的"，技能与结构保证"代码是好的"。
  先拿正确性，再谈品味。

## 4. 落地顺序（别倒着做）

1. **本地运行时验证 + 功能地图** → 让一个 agent 能独立复现一个真实问题（0 报错）。
2. **失败模式技能化** → 盯着 1–2 个 agent 的工具调用，把 3–5 个复发毛病写成技能。
3. **盲测爬坡** → 给核心技能定评分表，在伪装目录里跑，跨模型判分，改到满分。
4. **人工评论转硬检查** → 反复出现的评审意见变成 lint/AST/依赖图规则。
5. **云端队列与角色分工** → 先放一个"复现专员"，再上协调者与并行工人。

只有第 1 步稳了，第 5 步才不是烧钱。每一步的验收标准与"什么时候可以进下一步"见
`references/adoption-playbook.md`。

## 5. 每次交付前的自检

- [ ] 我的结论有**证据**（命令输出、页面状态、日志、diff），不是推断的语气？
- [ ] 我**真的运行过**要交付的东西，而不是"应该能跑"？
- [ ] 这个失败模式**下次还会发生吗**？要写进技能还是写进 lint？
- [ ] 这次改动**可以独立回滚**吗？（原子性）
- [ ] 我是否在替用户做他该做的决定（要授权/要偏好），而不是替他决定？

## 6. 反模式清单

- 用更多提示词解决结构问题。
- 把"agent 不可信"当结论，而不是当"缺验证机制"的症状。
- 只加技能不加硬检查——软约束会随时间腐化。
- 一次改 20 个文件再一起验证：失败时无法定位是哪一步。
- 让 agent 改测试的期望值来通过测试（这是最危险的"通过"）。
